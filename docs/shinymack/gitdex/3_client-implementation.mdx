# Client Implementation

The GitDex client is built using the Next.js App Router, leveraging a modern React stack to provide a highly interactive and responsive interface for repository analysis. The architecture focuses on a seamless onboarding experience, utilizing a combination of server-side layout configuration and client-side interactivity.

## Frontend Framework & Layout

The application utilizes the Next.js App Router for routing and layout management. The root layout serves as the primary wrapper, ensuring consistent styling, theme management, and global UI providers across all pages.

### Root Configuration
The `RootLayout` integrates several essential providers to maintain state and visual consistency:

| Provider | Source | Purpose |
| :--- | :--- | :--- |
| `ThemeProvider` | `next-themes` | Manages light/dark mode switching. |
| `RootProvider` | `fumadocs-ui` | Provides documentation-specific context and navigation. |
| `Toaster` | `sonner` | Handles global notification and toast alerts. |

The layout also implements custom typography using `MozillaHeadline` and `MozillaText` to maintain a distinct visual identity.

## Landing Page & Repository Onboarding

The entry point of the application (`app/page.tsx`) is designed as a high-conversion landing page that facilitates the transition from a GitHub URL to a GitDex analysis session.

### Repository Entry Workflow
The onboarding process follows a strict validation and selection pipeline to ensure that only valid GitHub repositories are processed.

```mermaid

    A["User Input"] ->> B["validateGitHubUrl()"]
    B -- "Valid" --> C["Fetch Suggestions"]
    B -- "Invalid" --> D["Show Error"]
    C ->> E["RepoSuggestion List"]
    E ->> F["handleSelectRepo()"]
    F ->> G["Redirect to Analysis"]
```

### Implementation Details

#### Data Models
The client defines a strict interface for repository suggestions to ensure type safety when handling GitHub API responses:

```typescript
interface RepoSuggestion {
  full_name: string;
  description: string;
  html_url: string;
}
```

#### Core Component Logic
The home page manages local state for user input and suggestion lists using React hooks (`useState`, `useEffect`, `useCallback`). Key logic includes:

*   **Validation**: Uses `validateGitHubUrl` to verify the format of the input before triggering API calls.
*   **Interaction**: Implements `handleKeyDown` for accessibility (Enter key submission) and `handleSelectRepo` for navigating to the specific repository analysis view.
*   **Client-Only Rendering**: Wraps interactive components in a `ClientOnly` wrapper to prevent hydration mismatches between the server and client.

### UI Component Architecture
The frontend employs a modular component strategy to separate visual effects from business logic.

| Component | Purpose | Key Feature |
| :--- | :--- | :--- |
| `ModernNav` | Site Navigation | Top-level navigation links. |
| `InteractiveConstellation` | Visual Engagement | Dynamic background visualization. |
| `FlickeringGrid` | Aesthetic Layer | Background grid effect. |
| `FeatureGrid` | Information Display | Highlighting core value propositions. |
| `WordRotate` | Dynamic Text | Animated text rotation for headlines. |

## Invariants & Failure Modes

To ensure stability during the repository onboarding process, the client implementation adheres to several architectural invariants and handles specific failure modes:

### Client-Side Invariants
*   **Hydration Safety**: Interactive components that rely on browser-specific APIs (like window size or local storage) are strictly wrapped in the `ClientOnly` component to avoid Next.js hydration errors.
*   **Input Sanitization**: All GitHub URLs are passed through `validateGitHubUrl` before being sent to the backend, preventing unnecessary API calls and potential injection attempts.

### Failure Modes & Handling
*   **Invalid URL Entry**: When `validateGitHubUrl` returns false, the system prevents the `handleSubmit` logic from executing and triggers a UI-level validation error.
*   **API Latency**: The use of `useState` for loading states (implied by the submit logic) ensures the user receives feedback while repository suggestions are being fetched.
*   **Malformed Repo Data**: The `RepoSuggestion` interface ensures that the application does not crash if the backend returns unexpected data structures, as the selection logic depends on specific properties (`full_name`, `html_url`).
