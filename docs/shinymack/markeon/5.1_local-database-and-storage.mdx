# Local Database and Storage

The Local Database and Storage module serves as the persistence layer for Markeon. Its primary responsibility is to ensure that user-generated content—including Markdown documents, custom themes, font configurations, and application metadata—is stored reliably within the browser, allowing for a seamless "offline-first" experience where data persists across sessions.

This module abstracts the complexities of the browser's underlying storage mechanism, providing a clean, promise-based API that the rest of the application uses to perform CRUD (Create, Read, Update, Delete) operations.

### Architectural Role

In the broader Markeon architecture, the storage layer sits beneath the state management system. While the application maintains an in-memory state for active editing and UI responsiveness, the `db.js` module acts as the "source of truth" that hydrates the application on startup and commits changes to disk.

| Store | Purpose | Primary Key |
| :--- | :--- | :--- |
| `files` | Stores Markdown document content and metadata | `id` |
| `attachments` | Handles binary data or links associated with documents | `id` |
| `themes` | Persists custom visual theme configurations | `id` |
| `fonts` | Stores user-defined font preferences | `id` |
| `meta` | Key-value store for global application settings | `key` |

### Component Interaction & Data Flow

The data flow follows a strict unidirectional path from the UI to the storage layer. When a user modifies a document or changes a setting, the application invokes the corresponding asynchronous function in `db.js`, which then interacts with the browser's database.

```mermaid
graph LR
    UI["UI Component"] --> Logic["App Logic"]
    Logic --> DB["db.js Wrapper"]
    DB --> IDB["IndexedDB"]
    IDB --> DB
    DB --> Logic
    Logic --> UI
```

For unique identifier generation, the system utilizes a lightweight, internal implementation of `nanoid`. This ensures that every document, theme, and attachment has a collision-resistant ID without introducing heavy external dependencies.

#### Document Persistence
The file management API provides high-level functions to handle the lifecycle of a Markdown document. The `saveFile` function is designed to be idempotent, handling both the creation of new documents and the updating of existing ones.

```javascript
export async function saveFile(file) {
  const db = await getDB();
  const tx = db.transaction('files', 'readwrite');
  await tx.store.put(file);
  await tx.done;
}
```

This pattern is mirrored across all stores. For example, the `themes` and `fonts` stores allow users to customize the editor's appearance, while the `meta` store provides a flexible way to save simple configuration pairs (e.g., `last_opened_file`).

#### Attachment Management
Because documents may contain multiple associated assets, the storage layer includes specialized logic for attachments. Beyond standard CRUD, it supports bulk deletion to maintain referential integrity when a parent document is removed.

```javascript
export async function deleteAttachmentsByIds(ids) {
  const db = await getDB();
  const tx = db.transaction('attachments', 'readwrite');
  for (const id of ids) {
    await tx.store.delete(id);
  }
  await tx.done;
}
```
