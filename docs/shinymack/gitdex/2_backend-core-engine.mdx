# Backend Core Engine

The Backend Core Engine serves as the orchestration layer of the GitDex ecosystem. It is responsible for managing the lifecycle of repository analysis jobs, coordinating between the GitHub API and LLM providers, and ensuring asynchronous task reliability via a distributed queue. The engine is implemented as a high-performance TypeScript server running on the Bun runtime, leveraging Express for request routing and middleware.

## System Role & Architectural Position

The Core Engine acts as the central controller that decouples client requests from long-running AI processing tasks. By utilizing a producer-consumer pattern via QStash and Redis, the system avoids request timeouts associated with heavy repository indexing and LLM token generation.

### Core Technology Stack & Dependencies

| Component | Implementation | Technical Purpose |
| :--- | :--- | :--- |
| **Runtime** | `Bun` | High-performance JS/TS runtime with native TypeScript support. |
| **API Framework** | `Express v5.2.1` | Routing, middleware orchestration, and request handling. |
| **Task Queue** | `@upstash/qstash` | Distributed scheduling and HTTP-based asynchronous job triggering. |
| **State Store** | `@upstash/redis` | Low-latency caching of job statuses and processed repository metadata. |
| **Repo Packaging** | `repomix` | Packing local/remote repositories into LLM-optimized contexts. |
| **AI SDK** | `ai` / `@google/genai` | Interface for Google Gemini and Vercel AI SDK integration. |
| **Tokenization** | `js-tiktoken` | Precise LLM context window calculations and token compression. |
| **GitHub Client** | `@octokit/rest` | Authenticated interaction with GitHub REST API. |

## Core Execution & Data Flow Mechanics

The engine processes repository analysis through a non-blocking pipeline. When a request to index a repository is received, the server does not process the data immediately; instead, it schedules a job and returns a tracking ID to the client.

### High-Level Job Orchestration Flow

```mermaid
graph LR
    A["Client Request"] --> B["Express Router"]
    B --> C["Job Controller"]
    C --> D["QStash Scheduler"]
    D --> E["Pipeline Worker"]
    E --> F["Repomix Packer"]
    F --> G["LLM Service"]
    G --> H["Redis Store"]
    H --> I["Client Polling"]
```

### Key Execution Invariants
*   **Asynchronous Decoupling**: All repository processing is offloaded to QStash to prevent HTTP 504 timeouts during large-scale file indexing.
*   **Stateless Processing**: The server maintains no local state; all job progress and AI outputs are persisted in Redis, allowing for horizontal scaling of the backend.
*   **Raw Body Integrity**: To maintain the security of QStash webhooks, the server captures the raw request buffer before JSON parsing to allow for cryptographic signature verification.
*   **CORS Strictness**: Access is restricted to a whitelist defined by `CLIENT_URLS` and `.vercel.app` domains to prevent unauthorized cross-origin AI service exploitation.

## Implementation Deep Dive

### Server Entry Point & Middleware Configuration

The server initialization focuses on security and the specific requirement of QStash signature verification.

```typescript title="server/index.ts"
// ... imports
const app = express();

// CRITICAL: Capture the raw body BEFORE parsing JSON, so QStash signature verification works
app.use(express.json({
  verify: (req: RequestWithRawBody, _res, buf) => {
    req.rawBody = buf.toString();
  }
}));

app.use("/api", jobsRoutes);
app.use("/api/dev", devRoutes);
```

**Mechanics:**
1.  **`RequestWithRawBody`**: Extends the standard Express `Request` type to include an optional `rawBody` string.
2.  **`express.json({ verify })`**: This hook intercepts the incoming stream. By assigning `buf.toString()` to `req.rawBody`, the engine preserves the exact byte sequence needed by `@upstash/qstash` to validate that the request originated from the trusted QStash service.
3.  **Route Segmentation**: The `/api` prefix separates production job logic from `/api/dev` diagnostic tools.

### Infrastructure Configuration

The system is configured for strict type safety and modern ESM resolution, as defined in the TypeScript configuration.

```json title="server/tsconfig.json"
{
  "compilerOptions": {
    "target": "ESNext",
    "module": "Preserve",
    "moduleResolution": "bundler",
    "allowImportingTsExtensions": true,
    "noUncheckedIndexedAccess": true,
    "strict": true
  }
}
```

**Configuration Rationale:**
*   **`module: Preserve` & `moduleResolution: bundler`**: Optimizes the build for Bun's native module resolution, enabling faster cold starts.
*   **`noUncheckedIndexedAccess`**: Forces explicit null checks when accessing arrays or maps, critical for preventing runtime crashes during the parsing of unpredictable repository file structures.

## Method / State Reference & Error Recovery

### API Endpoint Contract

| Endpoint | Method | Purpose | Expected Payload |
| :--- | :--- | :--- | :--- |
| `/health` | `GET` | Liveness probe for orchestrator | N/A |
| `/api/jobs` | `POST` | Trigger repository indexing | `{ repo: string, options: object }` |
| `/api/jobs/:id` | `GET` | Poll job status/result | N/A |
| `/api/dev/*` | `ANY` | Developer diagnostics | Variable |

### Failure Modes & Recovery

| Failure Scenario | Detection Mechanism | Recovery Strategy |
| :--- | :--- | :--- |
| **CORS Violation** | Express middleware check | Returns `Error('Not allowed by CORS')` $\rightarrow$ 403 Forbidden. |
| **QStash Sig Mismatch** | `rawBody` verification failure | Request rejected immediately; QStash triggers automatic retry based on backoff policy. |
| **LLM Context Overflow** | `js-tiktoken` count $> \text{Limit}$ | Implementation of token compression or chunking via `repomix` configuration. |
| **Unhandled Exception** | Global Error Middleware | Catches `Error` object, logs to stderr, returns 500 Internal Server Error to prevent leakage of system internals. |
